# 주문 체결 엔진 (Order Matching Engine)

매수·매도 주문을 받아 **가격 우선·시간 우선** 원칙에 따라 체결하는 간단한 체결 엔진입니다.
증권 거래소의 매매체결시스템이 하는 핵심 동작을 파이썬 기본 문법만으로 직접 구현했습니다.
주문 수량이 서로 다를 때 일부만 체결하는 **부분 체결**도 지원합니다.

## 1. 프로젝트 소개

거래소에서 "삼성전자를 98원에 사겠다"는 주문이 들어오면, 누군가의 매도 주문과 짝이 지어져야 거래가 성사됩니다.
이 짝을 지어주는 프로그램이 체결 엔진이며, 자본시장 IT 인프라의 가장 핵심적인 부분입니다.

이 프로젝트는 그 규칙을 직접 코드로 옮겨보며 체결 시스템의 동작 원리를 이해하기 위해 만들었습니다.
외부 라이브러리 없이 클래스, 리스트, 반복문만으로 구현했습니다.

## 2. 체결 규칙

체결 하나에는 세 가지 규칙이 따로 적용됩니다.

### 누구와 체결되는가

1. **가격 우선**: 매수 주문은 가장 싸게 팔겠다는 매도 주문과, 매도 주문은 가장 비싸게 사겠다는 매수 주문과 체결됩니다.
2. **시간 우선**: 가격이 같으면 먼저 들어온 주문이 우선입니다.

가격을 먼저 따지고, 시간은 **가격이 같을 때만** 따집니다.

### 체결되는 조건

매수 가격 ≥ 매도 가격일 때 체결됩니다. 조건이 맞지 않거나 반대편에 주문이 없으면 대기열에 들어가 기다립니다.

### 몇 원에 체결되는가

**먼저 들어와서 기다리고 있던 주문의 가격**으로 체결됩니다.
따라서 나중에 들어온 주문은 자신이 낸 가격과 같거나 더 유리한 가격에 체결됩니다.

| 기다리던 주문 | 새로 들어온 주문 | 체결 가격 | 이득을 본 쪽 |
|---|---|---|---|
| 매도 98원 | 매수 101원 | 98원 | 매수자 (3원) |
| 매수 97원 | 매도 96원 | 97원 | 매도자 (1원) |

### 몇 주 체결되는가

**두 주문의 수량 중 작은 쪽**만큼 체결됩니다. 자세한 내용은 6번 섹션에 정리했습니다.

## 3. 구조

| 구성 요소 | 역할 |
|---|---|
| `Order` | 주문 하나. 주문번호, 매수/매도 여부, 수량, 가격을 담음 |
| `buy_orders` | 체결되지 않은 매수 주문의 대기열 |
| `sell_orders` | 체결되지 않은 매도 주문의 대기열 |
| `find_best_sell()` | 매도 대기열에서 가장 싼 주문을 찾음 (같으면 먼저 온 주문) |
| `find_best_buy()` | 매수 대기열에서 가장 비싼 주문을 찾음 (같으면 먼저 온 주문) |
| `submit()` | 새 주문을 받아 체결하거나 대기열에 넣음 |

`submit()`의 동작은 다음과 같습니다.

```
새 주문 도착
  → 내 주문 수량이 남아 있는 동안 반복:
       반대편 대기열에서 가장 좋은 주문(best)을 찾는다
       best가 없거나 가격이 맞지 않으면 → 반복 종료
       체결 수량 = min(내 수량, best 수량)
       체결 결과를 출력하고, 양쪽 수량에서 체결 수량만큼 뺀다
       best 수량이 0이 되면 → best를 반대편 대기열에서 뺀다
  → 반복이 끝난 뒤 내 수량이 남아 있으면 → 내 쪽 대기열에 넣는다
```

모든 주문은 `submit()` 한 곳만 거쳐 들어옵니다. 체결 여부를 확인하지 않고 대기열에 들어가는 주문이 없도록 하기 위해서입니다.

## 4. 실행 방법

설치할 라이브러리는 없습니다. Python 3만 있으면 됩니다.

```
python matching.py
```

## 5. 테스트와 결과

실행 전에 손으로 결과를 예상하고, 실제 실행 결과와 비교했습니다. 모든 테스트가 예상과 일치했습니다.

### 기본 테스트 (수량이 모두 같을 때)

아래 8개 주문을 순서대로 넣었습니다.

| 번호 | 구분 | 가격 | 수량 |
|---|---|---|---|
| 1 | 매도 | 100원 | 10주 |
| 2 | 매도 | 98원 | 10주 |
| 3 | 매도 | 98원 | 10주 |
| 4 | 매수 | 99원 | 10주 |
| 5 | 매수 | 97원 | 10주 |
| 6 | 매수 | 101원 | 10주 |
| 7 | 매수 | 90원 | 10주 |
| 8 | 매도 | 96원 | 10주 |

```
4번 매수 주문 체결 완료: 2번, 98원, 10주
6번 매수 주문 체결 완료: 3번, 98원, 10주
8번 매도 주문 체결 완료: 5번, 97원, 10주
남은 매수: [(7, 90, 10)]
남은 매도: [(1, 100, 10)]
```

- **1~3번**: 반대편 대기열이 비어 있을 때 오류 없이 대기하는지
- **4번**: 같은 98원인 2번과 3번 중 먼저 온 2번과 체결되는지 (시간 우선)
- **5번, 7번**: 가격이 맞지 않으면 대기하는지
- **6번**: 100원(1번)보다 싼 98원(3번)과 체결되는지 (가격 우선)
- **8번**: 매도 주문도 체결되며, 기다리던 매수 주문의 가격(97원)으로 체결되는지

### 부분 체결 테스트

**테스트 1 — 새 주문이 더 작을 때**: 매도 98원 10주 대기 중, 매수 99원 4주 도착
```
2번 매수 주문 체결 완료: 1번, 98원, 4주
남은 매수: []
남은 매도: [(1, 98, 6)]
```
4주만 체결되고, 기다리던 매도 주문은 6주로 줄어 대기열에 남습니다.

**테스트 2 — 한 주문이 여러 상대와 체결될 때**: 매도 98원 4주, 98원 5주, 100원 10주 대기 중, 매수 99원 12주 도착
```
4번 매수 주문 체결 완료: 1번, 98원, 4주
4번 매수 주문 체결 완료: 2번, 98원, 5주
남은 매수: [(4, 99, 3)]
남은 매도: [(3, 100, 10)]
```
1번과 체결해 1번 수량이 0이 된 뒤에도 멈추지 않고 2번과 이어서 체결합니다. 남은 3주는 100원과 가격이 맞지 않아 대기열로 들어갑니다.

**테스트 3 — 매도 쪽 부분 체결**: 매수 99원 3주, 99원 5주, 97원 10주 대기 중, 매도 98원 10주 도착
```
4번 매도 주문 체결 완료: 1번, 99원, 3주
4번 매도 주문 체결 완료: 2번, 99원, 5주
남은 매수: [(3, 97, 10)]
남은 매도: [(4, 98, 2)]
```
매도 주문도 같은 방식으로 동작하며, 기다리던 매수 주문의 가격(99원)으로 체결됩니다.

## 6. 부분 체결 처리

### 매수 주문이 들어올 때

1. `find_best_sell(sell_orders)`로 매도 대기열에서 가장 좋은 상대(`best`)를 찾는다.
2. `min(order.order_quantity, best.order_quantity)`로 이번에 체결할 수량을 정한다. 두 수량 중 작은 쪽만큼만 체결할 수 있기 때문이다.
3. 체결한 뒤 **새 주문(`order`)과 상대(`best`) 양쪽의 수량**에서 체결 수량만큼 뺀다. 체결은 항상 양쪽에 동시에 일어나기 때문이다.
4. `best`의 수량이 0이 되면 `best`를 매도 대기열에서 뺀다. 그리고 **멈추지 않고 1번으로 돌아가 다음 상대를 찾는다.** 내 주문이 아직 남아 있을 수 있기 때문이다.
5. 반복은 다음 세 경우 중 하나가 되면 끝난다.
   - 내 주문 수량이 0이 됨 (전부 체결)
   - 반대편 대기열이 비어 있음 (`best`가 `None`)
   - 가장 좋은 상대와도 가격이 맞지 않음
6. 반복이 끝났을 때 내 주문 수량이 남아 있으면 매수 대기열에 넣고, 0이면 넣지 않는다.

일부만 체결되고 남은 주문은 대기열에서 빠졌다가 다시 들어가는 것이 아니라 **원래 자리에 수량만 줄어든 채로 남는다.** 그래서 시간 우선 순서가 그대로 유지된다.

### 매도 주문이 들어올 때

매수 주문과 같은 방식을 방향만 반대로 적용한다. `find_best_buy(buy_orders)`로 가장 비싼 매수 주문을 찾고, 내 가격이 그보다 높으면 멈추며, 수량이 0이 된 상대는 매수 대기열에서 빼고, 남은 수량은 매도 대기열에 넣는다.

### 취지

매수 및 매도 주문을 할 때 항상 모두 체결되는 것이 아닐 수 있다. 이번 공부를 통해 미완료된 주문은 어떻게 처리해야 하는지, 그리고 한 주문이 여러 상대와 나눠서 체결될 수 있다는 것을 알게 되었다.

## 7. 구현하며 배운 점

**금액은 float가 아닌 int로 저장했습니다.**
float는 소수를 2진수로 근사하기 때문에 `0.1 + 0.2 == 0.3`이 `False`가 됩니다.
체결 엔진은 "가격이 같은가"를 정확히 비교해야 시간 우선을 판단할 수 있으므로, 오차가 있는 float는 쓸 수 없습니다.

**동점일 때는 `<`를 쓰고 `<=`를 쓰지 않았습니다.**
가장 좋은 주문을 찾을 때 `<=`를 쓰면 같은 가격의 나중 주문으로 교체되어 시간 우선 원칙이 깨집니다.

**`best is None` 검사를 `or`의 왼쪽에 두었습니다.**
반대편 대기열이 비어 있으면 `best`가 `None`입니다. 이때 `best.stock_price`를 먼저 계산하면 `AttributeError`로 프로그램이 멈춥니다.
`or`는 왼쪽이 참이면 오른쪽을 실행하지 않으므로(단락 평가) `None` 검사를 반드시 앞에 두어야 합니다.

**테스트 하나를 통과했다고 코드가 맞는 것은 아니었습니다.**
- `find_best_buy`에서 `return`이 반복문 안에 들어가 항상 첫 번째 주문만 반환하는 버그가 있었는데, 테스트 데이터에서 정답이 우연히 첫 번째라 발견하지 못했습니다. 정답을 뒤에 둔 테스트를 추가해 찾았습니다.
- 주문을 미리 대기열에 넣어둔 상태에서 테스트를 맞추려고 `submit()`을 수정했다가, 새로 들어온 주문에서 오류가 났습니다. 결과에 맞춰 코드를 고치는 대신 원인(체결 확인 없이 대기열에 넣은 것)을 고쳐야 한다는 것을 배웠습니다.

## 8. 한계와 개선 방향

**시간복잡도**
`find_best_sell()`이 대기열 전체를 훑고, `remove()`도 지울 주문을 찾느라 한 번 더 훑습니다.
대기열에 주문이 n개면 상대 한 명과 체결하는 데 O(n), 주문 N개를 모두 처리하면 O(N²)입니다.
실제 거래소처럼 주문이 많아지면 감당할 수 없는 구조입니다.

**개선 방향**
- **힙(우선순위 큐) 사용**: 가장 좋은 주문이 항상 맨 위에 있으므로 찾기 O(1), 넣고 빼기 O(log n)으로 줄일 수 있습니다.
- **체결 기록 저장**: 체결 내역을 데이터베이스에 남겨 조회할 수 있게 할 수 있습니다.
- **주문 취소**: 대기 중인 주문을 취소하는 기능이 없습니다.
